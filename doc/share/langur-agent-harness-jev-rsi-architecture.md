# 一个 Agent 框架的自我修养：Langur 的三条架构哲学

> 会自我进化的 Agent，为什么不该失控？这篇文章不讲模块清单，只讲三件事：Langur 怎么把执行切成可替换的积木、怎么让"判断"与"生成"各司其职、又怎么给"自我改进"套上安全笼头。最后给一套你可以直接套用到自己项目里的方法论。

![Langur 全局架构](images/langur-global-architecture.png)

先说一个观察：市面上的 Agent 框架，多数死在三种写法上。

第一种，**把 LLM 调用封装成一个函数**。`chat(messages, tools) -> 决策`，一个函数打天下。它的问题不是功能少，而是"换模型、换记忆、换存储"时，你得顺着调用链一路改下去。

第二种，**把执行、工具、记忆、状态揉成一坨**。一个 `AgentRunner` 类里既跑 ReAct 循环、又管工具注册、还自己维护会话状态。加一个能力，就多一层不敢动的历史包袱。

第三种，**把"自我改进"做成黑盒**。让 Agent 直接改自己的提示词、改自己的路由，看似高级，实则失控——你根本说不清哪次修改让它在生产上翻车了。

Langur 想反着来。它只坚持三条架构哲学，每一条都在回答一个"为什么"。

## 哲学一：正交——架构的本质是切边界，边界的本质是端口

一次 Agent 执行，Langur 把它切成六个组件：

![Harness 六要素](images/langur-harness-six-components.png)

执行（E）、工具（T）、上下文（C）、状态（S）、生命周期（L）、可观测（V）。六块积木，各自独立。

这里有个反直觉的点：**拆得越碎，反而越敢改**。因为组件之间只靠端口通信——E 不关心 T 的工具有几层校验，T 不关心 C 的记忆存在哪。于是：

- 把内存向量库换成 Elasticsearch，只动基础设施层，E/T/C/S/L/V 一行不改；
- Redis 挂了，缓存和分布式锁静默降级到内存，主链路不断；
- 每个组件都能离线单测，不依赖真实的大模型、Redis、向量库。

更关键的是那条容易踩的坑：**决策平面不能成为第七个组件**。一旦它变成一个"竖井组件"，六组件的正交就崩了，回到"揉成一坨"的老路。所以 Langur 让决策平面经依赖注入**横切**进 E/T/C 各消费点，缺失即降级，不给任何组件添硬依赖。

这套切法在工程上有个名字：**依赖倒置**。领域层定义端口（`LLMPort`、`VectorStore`、`DecisionPort`……），基础设施层实现端口。于是"换一家大模型、换一个向量库"从来不是改领域代码，是改配置文件。这是正交能成立的地基。

## 哲学二：能用廉价判断解决的，绝不烧昂贵的生成

大模型（System-2）擅长生成，但不擅长高频、廉价、可标定的**判断**。Langur 引入一个决策平面，用 Jev 这类判定模型做 System-1：

![Jev 决策平面](images/langur-jev-decision-plane.png)

一个 `DecisionPort` 端口，输入问题，返回 `choice / probability / score` 加上**置信度**。外面包一条装饰链：录制 → 缓存 → 阈值路由 → 后端 → 规则兜底。

这套设计最值钱的是它背后的**判定/生成分离**：判断走决策平面，生成走 LLM，二者彻底解耦。落到 10 个执行插入点上——Workflow 阶段闸门、审批风险分级、产物验收、ReAct 完成/卡死判定、Skill 的 DECISION 步骤……

为什么值得做？因为"该不该继续、该不该跳过、该不该审批"这类判断，如果每次都烧一次大模型推理，就是白烧钱。用廉价的判定模型先过一遍，只有需要时才升级到 System-2。

但它有一条碰不得的红线：**决策平面对安全/审批闸门永远只是"建议"，只收紧、不放松，低置信一律回退兜底**。CRITICAL 审批永远要人来拍板，决策平面顶多给一份"风险摘要"帮人加速。判断层帮你提效，但永远夺不走安全兜底。

## 哲学三：能自我修改的系统，最大的敌人是自己

这是 Langur 最有想象力、也最危险的部分——递归自我改进（RSI）：回放、反思、蒸馏、自合成技能、自我调优、自扩展工具。

![RSI 递归自我改进](images/langur-rsi-self-improvement.png)

危险在于：一个能改自己提示词和路由的系统，怎么保证它不会越改越糟、甚至绕过安全策略？

Langur 的答案是一句话：**所有自我改进的产物，默认都只是"候选提案"，必须过三道关——回放验证、灰度、高危人审——才能生效。**

第一道关是**回放验证**：把历史执行轨迹和录制的判定离线重放一遍，拿候选和基线做反事实对比。三个拒绝条件写死在引擎里：劣化即拒绝、放松审批闸门即拒绝、**回放通过也不等于生效**——回放只是第一道关，不是放行令。

第二道关是**安全平面统辖**：提案要走"提案-验证-应用"三段式状态机，外加四道护栏——权限隔离红线（动安全策略层直接拒）、高危强制人审、递归深度上限、变更频率限流，且全程可一键回滚。

这套设计有个很妙的闭环：Jev 帮 Agent 判断，但 Jev 自己的阈值/路由要变，同样是一个受安全平面管辖的提案。**连"判断器"都不例外，这才叫真的统辖。**

## 地基：架构是"守"出来的，不是"画"出来的

三条哲学能落地，靠的是一个扎实的 DDD 六边形地基：

![DDD 六边形分层](images/langur-ddd-hexagonal.png)

```
start → api → application → domain ← infrastructure
```

方向严格单向。最核心的一条：**领域层零外部依赖**——不 import Spring、不 import 基础设施，只依赖公共契约。代价是领域层不能直接记日志、不能直接用 `@Component`，全部靠端口和手动装配；收益是两百多项领域测试全部纯 JUnit5、零 Mockito、零网络，离线确定性跑完。

更重要的是，这些"红线"不是写在文档里的空话，而是用 **ArchUnit** 写死的可执行断言——`domain 不依赖 Spring/infrastructure`、`api 不直调 domain`、`分层无环`，随每次测试一起跑。架构是"守"出来的：把约定变成检查，把检查变成 CI 里的一票否决。

## 拿走就能用的五条方法论

如果你也在做 Agent 或类似的中台系统，这五条可以直接套：

1. **用端口切边界**：先问"哪几块可以独立替换、独立测试、独立降级"，再决定怎么拆。切完用端口连，别用 import 连。
2. **依赖倒置**：让核心逻辑定义接口、让外部依赖实现接口。判断标准很简单——换一个外部依赖，核心代码一行不改，就对了。
3. **判断与生成分层**：凡是"该不该/要不要/行不行"的高频判断，都值得一条廉价通道，别每次都烧大模型。
4. **自改进套三关**：任何"系统改自己"的能力，默认产物当候选，过回放、灰度、人审，且能回滚。连判断器自己都不例外。
5. **红线可执行**：把最重要的架构约束写成自动化断言，让它在 CI 里拦人，而不是靠 code review 的口头约定。

## 号召开源共建

Langur 的这套设计已经全部落地，累计 600+ 项离线测试全绿。但一个 Agent 框架的进化，不该只是一个人的事。

如果你对下面任何一个方向感兴趣，欢迎一起共建：

- **决策平面**：接入更多判定模型后端，把 10 个插入点用到更多场景；
- **自我改进**：让"回放 + 灰度 + 人审"的闭环跑在真实业务上，验证这套安全范式；
- **基础设施**：补齐更多模型厂商、更多向量库，让"换模型、换存储"始终是改配置；
- **工程治理**：把上面那五条方法论，推广到更多项目。

代码在 [github.com/Jashinck/Skylark](https://github.com/Jashinck/Skylark)（Langur 为其 Agent 框架子项目），设计文档随仓库开源，每一笔能力落地都有记录可追溯。

**如果你也在做 Agent，或者对"正交 + 判定分层 + 自改进护栏"这套范式有想法，欢迎提 issue、提 PR、一起讨论。** 让叶猴再轻盈一点，也再聪明一点。
